1. Deployment Overview

This specification defines the requirements for deploying the Universe Reinsurance Platform (repository name: modelling_tool) in a corporate work environment. It is intended for internal IT administrators responsible for provisioning, configuring, securing, monitoring, and releasing the platform into production. Follow the sections in sequence to achieve a clean and repeatable deployment.

  1. Update the operating system: sudo apt update && sudo apt upgrade -y
  2. Install Node.js 20.18.0 (NodeSource or nvm)
  3. Install PostgreSQL and create the database user (§4)
  4. Install Git and configure GitHub access (§6.1) — password authentication no longer works; a token or SSH deploy key is required
  5. Clone the repository (§6.2)
  6. Install PM2 globally; install Nginx; install Redis if clustering
  7. Create and secure the .env file from .env.example (§5)
  8. Run npm run install:all, then npm run build
  9. Run database migrations: npm run migrate:up --prefix server
  10. Start the application: pm2 start ecosystem.config.cjs
  11. Configure the Nginx reverse proxy (§7)
  12. Install and validate the SSL certificate
  13. Schedule backups (§4.3) and verify health endpoints (§10)

4. Database Setup

4.1 PostgreSQL Installation and Initial Configuration

# Install PostgreSQL
sudo apt install -y postgresql-16 postgresql-contrib
sudo systemctl enable --now postgresql

# Create the database user and database
sudo -u postgres psql <<SQL
CREATE USER universe WITH PASSWORD 'CHANGE_ME_STRONG_PASSWORD';
CREATE DATABASE universe OWNER universe;
GRANT ALL PRIVILEGES ON DATABASE universe TO universe;
SQL

The resulting connection string is:

DATABASE_URL=postgresql://universe:CHANGE_ME_STRONG_PASSWORD@localhost:5432/universe

URL-encoding: if the password contains URL-special characters (@ : / # %), URL-encode them — e.g. Sahara@66 becomes Sahara%4066.

For a separate database host, install postgresql-client-16 on the app server, allow the app server's IP in pg_hba.conf on the DB host, and append ?sslmode=require to DATABASE_URL.

4.2 Connection Sizing

Postgres max_connections defaults to 100. The app's per-process pool default is 50 (DB_POOL_MAX). Leave at least 30 connections free for migrations, ad-hoc queries, and monitoring. In PM2 cluster mode each worker has its own pool — ecosystem.config.cjs automatically derives a safe per-worker DB_POOL_MAX (total ≤ 80), but verify workers × DB_POOL_MAX < max_connections if you override anything.

For a 16 GB server, baseline tuning in /etc/postgresql/16/main/postgresql.conf: shared_buffers = 4GB, effective_cache_size = 12GB, maintenance_work_mem = 1GB, checkpoint_completion_target = 0.9, wal_buffers = 64MB, random_page_cost = 1.1, work_mem = 40MB. Scale these down proportionally on smaller hosts.

4.3 Backup Schedule (use the checked-in scripts)

The repository ships restore-verified backup tooling — do not hand-write pg_dump cron lines.

ScriptWhat it does
scripts/backup-db.shCompressed pg_dump -Fc of DATABASE_URL into BACKUP_DIR (default /var/backups/universe); prunes dumps older than BACKUP_RETENTION_DAYS (default 30)
scripts/verify-restore.shRestores the newest dump into a throwaway scratch DB, sanity-checks it, and exits non-zero if the dump won't restore — catches silently corrupt backups
scripts/backup-uploads.shBacks up the uploads directory (slips and documents) alongside the database
scripts/universe-backup.cronHost-cron schedule: nightly dump at 02:00 + weekly restore rehearsal (Sun 03:30)
# Install the schedule (set DATABASE_URL in the cron environment first)
crontab scripts/universe-backup.cron     # or copy into /etc/cron.d/

# One-off manual verification
DATABASE_URL=postgresql://universe:PASSWORD@localhost:5432/universe \
BACKUP_DIR=/var/backups/universe scripts/backup-db.sh
DATABASE_URL=postgresql://universe:PASSWORD@localhost:5432/universe \
BACKUP_DIR=/var/backups/universe scripts/verify-restore.sh   # exit 0 = restorable

Copy dumps to off-host storage daily, retain ≥30 daily dumps, and document a monthly restore test. A backup that has not been restored successfully is not a verified backup.

Boot-time secret gate: with NODE_ENV=production the server validates secrets before serving and exits with a clear error if AUTH_JWT_SECRET is missing, a placeholder, or shorter than 32 characters. It also logs [posture] warnings at startup for risky-but-valid settings (no durable upload storage, no REDIS_URL while multi-instance, SSO/MFA gaps) — review and clear these before go-live.

5.2 Generating Secure Secrets

# Auth token secret (also fine for SESSION_SECRET)
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
# or
openssl rand -hex 64

# Database password
openssl rand -base64 32

6. Application Deployment

6.1 GitHub Access — Read This Before Cloning

GitHub no longer accepts account passwords for Git operations. Attempting to clone over HTTPS and typing your GitHub password produces: remote: Invalid username or token. Password authentication is not supported for Git operations. Also note the repository has moved: the old iwadaya/universe and iwadaya/claude_universe URLs are dead — the current private repository is Darchville-Analytics/modelling_tool.

Option 1 — Fine-grained Personal Access Token (recommended for HTTPS):

  1. On GitHub: Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Resource owner: Darchville-Analytics; Repository access: Only select repositories → modelling_tool; Permissions: Contents: Read-only. Set a 90-day expiry (rotate per §9.2).
  3. On the server, store the credential once for the deploy user, then clone. When prompted, username is your GitHub username and the password is the token, not your GitHub password:
sudo -u universe -H git config --global credential.helper store
sudo -u universe -H git clone \
    https://github.com/Darchville-Analytics/modelling_tool.git /opt/universe
# Username: <your-github-username>
# Password: <paste the fine-grained PAT>

The token is saved (mode 600) in ~universe/.git-credentials, so subsequent git pull during deploys will not prompt.

Option 2 — SSH deploy key (no token to rotate on the server):

sudo -u universe -H ssh-keygen -t ed25519 -C "universe-deploy" -N "" \
    -f /home/universe/.ssh/id_ed25519
sudo -u universe -H cat /home/universe/.ssh/id_ed25519.pub
# Add this public key on GitHub: repo -> Settings -> Deploy keys ->
# "Add deploy key" (leave "Allow write access" unticked)
sudo -u universe -H git clone \
    git@github.com:Darchville-Analytics/modelling_tool.git /opt/universe

Migrating an existing checkout that still points at the old URL:

cd /opt/universe
git remote set-url origin https://github.com/Darchville-Analytics/modelling_tool.git
git fetch origin && git pull origin main

6.2 Repository Setup

Create a dedicated application user and deploy into /opt/universe. Do not run the application as root.

# Create dedicated system user
sudo useradd -m -s /bin/bash universe

# Clone (after configuring access per 6.1) and take ownership
sudo -u universe -H git clone \
    https://github.com/Darchville-Analytics/modelling_tool.git /opt/universe
cd /opt/universe

# Install dependencies for root, client, and server; build the frontend
npm run install:all
npm run build

6.3 Deployment Script

The repository ships deploy.sh at the repo root — use it rather than writing your own. It pulls main, runs npm ci for root/client/server (reproducible installs from the lockfiles), rebuilds the frontend, applies migrations, and reloads PM2:

chmod +x /opt/universe/deploy.sh
/opt/universe/deploy.sh

6.4 Database Migrations

Migrations live in server/src/db/migrations/, run in single transactions with savepoints, are idempotent, and are guarded by a Postgres advisory lock (cluster workers cannot double-apply). They do not run on boot in production — run them as an explicit pre-deploy step so a bad migration fails the deploy instead of taking the running version down:

npm run migrate:status --prefix server   # show applied vs. pending
npm run migrate:up     --prefix server   # apply all pending

6.5 PM2 Configuration

Use the bundled ecosystem.config.cjs — do not start with ad-hoc flags. It configures cluster mode (workers = CPU count, capped at 4; override with PM2_INSTANCES), a derived per-worker DB_POOL_MAX, graceful reload timing, memory-limit restarts, merged logs, and PRICING_STRICT=1:

cd /opt/universe
pm2 start ecosystem.config.cjs
pm2 save
pm2 startup     # follow the printed command to enable on-boot start

Cluster mode requires REDIS_URL: rate limits are per-process without it, so 4 workers would allow 4× the intended ceiling. The production posture check logs a warning if this is missed.

6.6 Alternative Runtimes

The repo also supports Docker Compose (bundled Dockerfile + docker-compose.yml; review before production use — the compose file carries development defaults) and systemd (single-process, hardened unit file example). Full recipes are in DEPLOYMENT.md §6.2–6.3. Pick one runtime; do not mix them.

7. Nginx Reverse Proxy and SSL

Nginx terminates HTTPS and forwards all traffic to the Node.js app on port 4000. Unlike v1.0, Nginx does not serve client/dist directly — Express serves the SPA itself, so a single location / proxy block suffices.

7.1 Nginx Site Configuration

Create /etc/nginx/sites-available/universe:

server {
    listen 80;
    server_name universe.internal.company.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name universe.internal.company.com;

    ssl_certificate     /etc/ssl/universe/cert.pem;
    ssl_certificate_key /etc/ssl/universe/key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    server_tokens off;
    add_header Strict-Transport-Security "max-age=31536000" always;

    client_max_body_size 50M;   # matches the app's 50 MB upload limit

    location / {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
        proxy_read_timeout 60s;
    }
}
sudo ln -s /etc/nginx/sites-available/universe /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

9.3 Security Hardening Checklist

  • Disable root SSH login and SSH password authentication.
  • Enable automatic security updates (unattended-upgrades); install fail2ban.
  • Run the app as the non-root universe user; keep Node/Postgres/Nginx on supported versions.
  • PostgreSQL: listen_addresses = 'localhost' (or private subnet only); enable TLS for remote DB connections.
  • Nginx: server_tokens off, HSTS header enabled (the app itself already ships an enforcing nonce-based Content-Security-Policy via Helmet — do not add a conflicting CSP in Nginx).
  • Never set ALLOW_DEMO_AUTH or ALLOW_OPEN_REGISTRATION in production.
  • Enable ClamAV upload scanning (CLAMAV_ENABLED=true) with a reachable clamd.
  • Rotate or deactivate seeded accounts after first login (§11.5).

12. Common Issues and Troubleshooting

12.1 Git Clone or Pull Fails: "Password authentication is not supported"

Symptom: remote: Invalid username or token. Password authentication is not supported for Git operations. fatal: Authentication failed.

Causes and fix, in order:

  1. Wrong URL: the repository moved — use https://github.com/Darchville-Analytics/modelling_tool.git, not any iwadaya/… URL. For an existing checkout: git remote set-url origin https://github.com/Darchville-Analytics/modelling_tool.git.
  2. Password typed at the prompt: GitHub removed password auth for Git in 2021. At the password prompt paste a fine-grained personal access token (§6.1 Option 1), or switch to an SSH deploy key (§6.1 Option 2).
  3. Token rejected: confirm the token's resource owner is Darchville-Analytics, it includes modelling_tool, has Contents: Read, has not expired, and (for org repos) has been approved by an org admin.
  4. Prompted on every pull: enable the credential store for the deploy user: sudo -u universe -H git config --global credential.helper store, then pull once and enter the token.

12.2 Application Returns 500 Errors

pm2 logs universe --err --lines 30. Common causes: missing .env variable, failed DB connection, or migrations not run.

12.3 Server Exits Immediately on Start (Production)

The boot-time secret gate is working as designed: set a strong AUTH_JWT_SECRET (§5.1). The startup log states exactly which check failed.

12.4 Cannot Connect to the Database

sudo systemctl status postgresql, then verify the URL with psql "$DATABASE_URL" -c "SELECT 1". ECONNREFUSED ::1:5432 means Postgres is down or DATABASE_URL is wrong. Check pg_hba.conf permits the connection; remember to URL-encode special characters in the password.

12.5 Nginx 502 Bad Gateway

Node is not listening on port 4000 (or proxy_pass doesn't match PORT):

pm2 status
ss -tlnp | grep 4000
pm2 restart universe   # if stopped

12.6 Uploads Fail with 503 STORAGE_NOT_DURABLE

Production requires durable upload storage. Set CLOUDINARY_URL, or on a single box with a persistent volume set ALLOW_LOCAL_UPLOADS=true (§5.1). A 503 on upload with CLAMAV_ENABLED=true can also mean clamd is unreachable — check CLAMAV_HOST/CLAMAV_PORT.

12.7 Login Screen Lists No Users / Login Fails After Fresh Install

Reference data didn't seed or migrations didn't run. Tail the logs for migration errors and re-run npm run migrate:up --prefix server.

12.8 Migration Fails

Read the SQL error — it identifies the failing statement. Migrations roll back atomically, so the DB is never half-applied; permission denied usually means the GRANT ALL from §4.1 was missed. Re-run after fixing — migrate:up is idempotent.

12.9 PM2 App Keeps Restarting

pm2 logs universe --err. Typical causes: missing env variables (see 12.3), port conflict on 4000, or a worker exceeding the 1 GB memory ceiling (check for max_memory_restart events in pm2 show universe).

12.10 HTTPS Certificate Error

sudo nginx -t; if Let's Encrypt is used, sudo certbot renew.

Appendix B. Production Readiness Summary

The deployment is production-ready only when the following are all true:

  • HTTPS works using an approved certificate; HSTS enabled; server_tokens off.
  • SSH is key-only and restricted to authorised administrators.
  • PostgreSQL and Redis are not externally exposed.
  • The application runs under the non-root universe user via ecosystem.config.cjs, with pm2 save + pm2 startup done.
  • AUTH_JWT_SECRET is a strong generated secret; no [posture] warnings remain at startup.
  • Durable upload storage is configured; ClamAV scanning is enabled (or the risk is formally accepted).
  • GitHub access uses a scoped fine-grained PAT or read-only deploy key — never an account password.
  • Backups run automatically via scripts/universe-backup.cron and verify-restore.sh passes; restore tests are documented monthly.
  • Seeded accounts have been rotated or deactivated; monitoring and alerting are active.
  • The full go-live checklist (§11) has been signed off.
